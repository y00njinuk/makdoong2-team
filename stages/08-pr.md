# 7단계: Pull Request 생성 (Publisher 직접 실행)

**목적**: 리뷰 가능한 PR 을 만든다.
**진입 게이트**: `verify.sh <이슈키> 3_delivery.pr` — **전제조건만** 검사한다. 6단계 커밋 완료 + worktree clean + 현재 브랜치 확인 가능. 원격 push 존재 여부는 본 단계의 **완료 조건**이므로 진입 게이트가 아니라 §완료 후 검증(`verify.sh 3_delivery.pr_post`)에서 확인한다. remote push · createPullRequest 는 본 단계에서 publisher 가 수행한다.
> `git push` 자체도 PreToolUse 훅이 동일 게이트 (`3_delivery.commit.done == true`) 로 검증하므로, 전제 미충족 시 push 가 차단된다. push 가 통과하면 게이트도 통과한다.
> **PUBLISHER 전용 단계.** `git push` 및 Bitbucket MCP `createPullRequest` 는 publisher 가 worktree 에서 직접 실행한다. 부장님(team-leader) 은 git 명령 permission 이 deny 되어 있어 실행할 수 없다.

## 7-1. 사전 확인

게이트가 자동 검증하지만 의미상 다음이 모두 true여야 한다: 단위·통합 테스트가 둘 다 pass 또는 skip, 모든 커밋 완료, `git status` clean, remote push 완료. 하나라도 false면 해당 단계로 복귀.

## 7-2. PR 본문 (`references/pr-template.md` 참조)

```markdown
#### 목표
- <이슈 최종 목적>
#### 구현내용
- <실제 구현한 기능 단위>   # 파일 단위로 쓰지 않는다
#### Test
- "<테스트 시나리오 한글 문장>"
```
- **목표**: Jira acceptance criteria를 자연어로.
- **구현내용**: 추가·수정한 **기능 단위**로 나열.
- **Test**: 실제 시나리오를 큰따옴표 한글 문장으로.

## 7-3. PR 본문 검증 (생성 전 필수)

7-2에서 작성한 PR 본문을 임시 파일(예: `/tmp/pr-body.md`)에 저장한 뒤,
**PR 생성 전에 다음 세 가지를 모두 통과시킨다.** 하나라도 통과 못 하면 본문을 고치고
다시 검증한다. **통과 전엔 PR을 생성하지 않는다.**

### ① 테스트 코드 없는 시나리오 금지

`#### Test` 섹션의 각 시나리오 문장은, 이 브랜치에 추가/수정된 **실제 테스트 코드**로 1:1
매핑되어야 한다(시나리오 하나당 그것을 검증하는 테스트 메서드/케이스 하나).

이번 브랜치의 변경된 테스트 파일 확인:
```bash
git diff origin/main...HEAD --name-only -- \
  '*Test*.scala' '*Spec*.scala' '*Test*.java' '*.spec.ts' '*_test.go' 'test_*.py'
```

각 시나리오를 위 파일들 중 어떤 테스트가 검증하는지 스스로 확인한다. 매핑되지 않는
시나리오가 하나라도 있으면 → 시나리오를 제거하거나 누락 테스트를 작성. 매핑 0개인
"테스트 시나리오로만 존재하는" 항목은 PR 본문에 남기지 않는다.

### ② 템플릿 markdown 형식 준수

PR 본문은 `references/pr-template.md`가 정의한 `####` 헤딩 셋을 **정확히 그 순서로** 가진다.

```bash
grep -E '^#### ' /tmp/pr-body.md
```

> `<SCRIPTS_DIR>`는 부장님이 dispatch_stage 프롬프트로 주입한 절대경로다. 이 값을 그대로 대입하여 실행한다.
출력이 **정확히** 다음과 같아야 한다(추가도, 누락도, 순서 어긋남도 금지):
```
#### 목표
#### 구현내용
#### Test
```
- 헤딩 누락 → 추가.
- 임의 추가(예: `#### 비고`, `#### 참고`, `#### 영향도`) → 제거 또는 다른 섹션으로 흡수.
- 순서 다름 → 재정렬.

### ③ 항목 내용 적합성

각 섹션 내용이 그 섹션 성격에만 맞는지 자기검열:

- `#### 목표`: 이슈의 최종 목적(자연어 1~2문장). 구현 세부·테스트 시나리오 혼입 금지.
- `#### 구현내용`: 추가·수정한 **기능 단위** 나열. 파일 단위 나열 금지, 시나리오 문장 금지.
- `#### Test`: 큰따옴표 한글 시나리오 문장만. 코드 인용·구현 세부 금지.

빈 섹션(placeholder만 남음) 금지 — 해당 사항이 정말 없으면 누락 사유를 해소한다.

### 검증 결과 기록 (셋 다 통과 후에만)

```bash
bash <SCRIPTS_DIR>/state.sh set <이슈키> '.stages."3_delivery".substages."pr".body_validation' \
  '{"no_orphan_scenarios": true, "template_match": true, "section_content_match": true}'
```

> 8단계 진입 게이트가 위 세 플래그를 모두 `true`로 검증한다. 하나라도 false/누락이면
> 차단되어 다시 7-3을 통과해야 한다.



## 7-4. 생성 실행 (`bitbucket-research`의 PR 작성 규칙)

### 토큰 소유자 식별 (리뷰어 추가용)

API 호출로 `X-AUSERNAME` 응답 헤더를 확인하여 토큰 소유자의 username을 식별한다:

```bash
TOKEN=$(jq -r '.secrets.BITBUCKET_API_TOKEN' ~/.config/opencode/makdoong2-team.json)
BB_BASE=$(jq -r '.hosts.BITBUCKET_API_BASE_PATH' ~/.config/opencode/makdoong2-team.json)
USERNAME=$(curl -sI -H "Authorization: Bearer $TOKEN" \
  "$BB_BASE/api/latest/application-properties" \
  | grep -i '^X-AUSERNAME:' | awk '{print $2}' | tr -d '\r')
```

### PR 생성 규칙

- 반드시 **Draft로 생성** (`draft=true`).
- **토큰 소유자를 리뷰어로 자동 추가** (`reviewers=["$USERNAME"]`).
- 제목: `[이슈키] 짧은 요약` (예: `[PROJ-12345] 상품 캐시 조회 API 구현`).

`bitbucket_createPullRequest` 호출 시 위에서 식별한 `USERNAME`을 reviewers 파라미터에 포함한다.

> **자기 리뷰어 예외**: Bitbucket DC는 PR 작성자 자신을 reviewer로 추가하는 것을 허용하지 않는다. `bitbucket_getPullRequest` 재조회 후 `reviewers` 배열이 비어 있고, 토큰 소유자(`$USERNAME`)가 PR 작성자(`author.user.name`)와 동일한 경우, 이를 정상 상태로 처리하고 아래 완료 기록에서 `reviewer_self_skipped=true`를 사용한다.

## 7-5. 최종 자가 검증 (Pre-Completion Checklist)

PR 생성 직전 추가 5체크. 7-3 PR 본문 검증과 별개로, 단계 종료 자체에 대한 자체 점검.
하나라도 false면 PR 생성·완료 기록 금지.

| 항목 | 확인 |
|---|---|
| 1 | PR 본문이 `####` 헤딩 3개(목표/구현내용/Test)를 정확한 순서로 가진다 (7-3 ② 통과) |
| 2 | `#### Test` 시나리오 ↔ 실제 테스트 코드의 1:1 매핑이 확인되었다 (7-3 ① 통과) |
| 3 | 각 섹션 내용이 그 섹션 성격에 맞고, 빈 섹션이 없다 (7-3 ③ 통과) |
| 4 | Draft로 생성되며 리뷰어를 추가했거나(`reviewer_added=true`), 토큰 소유자 = PR 작성자이어서 skip했다(`reviewer_self_skipped=true`) |
| 5 | PR 제목이 `[이슈키] 짧은 요약` 형식이다 |

```bash
bash <SCRIPTS_DIR>/state.sh set <이슈키> '.stages."3_delivery".substages."pr".self_check' \
  '{"template_match": true, "scenario_test_paired": true, "section_content_match": true, "draft_with_reviewer": true, "title_format": true}'
```

## 완료 기록

PR 생성 직후, `bitbucket_getPullRequest`로 PR 상세를 재조회하여 `reviewers` 배열을 확인한다.

- **리뷰어가 있는 경우**: `reviewer_added=true` 기록.
- **리뷰어 배열이 비어 있는 경우**:
  - 토큰 소유자(`$USERNAME`) == PR 작성자(`author.user.name`)이면 → **자기 리뷰어 예외**: `reviewer_self_skipped=true` 기록. `reviewer_added`는 기록하지 않는다.
  - 그 외 → `bitbucket_updatePullRequest`로 reviewer를 추가한 뒤 재확인 후 `reviewer_added=true` 기록.

**두 마커 중 하나도 기록하지 않고 완료 선언 금지.**

```bash
bash <SCRIPTS_DIR>/state.sh set <이슈키> '.stages."3_delivery".substages."pr".draft_url' '"<생성된 PR URL>"'
# 아래 두 줄 중 실제 상황에 맞는 하나만 기록한다
bash <SCRIPTS_DIR>/state.sh set <이슈키> '.stages."3_delivery".substages."pr".reviewer_added' 'true'        # 리뷰어 추가 성공
bash <SCRIPTS_DIR>/state.sh set <이슈키> '.stages."3_delivery".substages."pr".reviewer_self_skipped' 'true' # 자기 자신이 PR 작성자여서 skip
bash <SCRIPTS_DIR>/state.sh set <이슈키> '.stages."3_delivery".substages."pr".done_at' "\"$(date -u +%Y-%m-%dT%H:%M:%SZ)\""
bash <SCRIPTS_DIR>/state.sh set <이슈키> '.stages."3_delivery".substages."pr".verification_pending' 'true'
# 사용자가 Draft PR을 검토하고 8단계 진행을 승인한 직후에만:
bash <SCRIPTS_DIR>/state.sh set <이슈키> '.stages."3_delivery".substages."pr".approved_by_user' 'true'
bash <SCRIPTS_DIR>/state.sh set <이슈키> '.stages."3_delivery".substages."pr".approved_at' "\"$(date -u +%Y-%m-%dT%H:%M:%SZ)\""
bash <SCRIPTS_DIR>/state.sh set <이슈키> '.stages."3_delivery".substages."pr".verification_pending' 'false'
```

## 완료 후 검증 (post-verify · 필수)

publisher 는 `.done=true` 를 기록하기 **직전** 완료 조건 재검증을 실행한다. 실패 시 exit 2 로 재작업 loop 를 트리거한다.

```bash
bash <SCRIPTS_DIR>/state.sh set <이슈키> '.stages."3_delivery".substages."pr".done' 'true'
bash <SCRIPTS_DIR>/../gates/stage7-post-pr-verify.sh <이슈키>
```

검사 대상 (모두 통과해야 done 유지):
- `origin/<current-branch>` 원격 브랜치 존재 (git push 성공)
- `.draft_url` 이 HTTPS URL 문자열
- `body_validation` 3항목 모두 true
- reviewer 마커 상호 배타 (reviewer_added=true XOR reviewer_self_skipped=true)
- `.done == true`

post-verify 실패 시:
1. stderr 의 `MAKDOONG2-POSTGATE BLOCKED` 사유를 읽는다
2. 해당 조건을 충족시키는 조치 수행 (예: git push 재시도, reviewer 재추가, draft_url 재기록)
3. `.done` 을 다시 `true` 로 설정하고 post-verify 재실행
4. 통과할 때까지 반복. 통과 후 부장님에게 결과 요약 출력




## 7-7. publisher 세션이 반복 실패할 때 (대체 경로)

`dispatch_stage(3_delivery.pr)` 가 **연속 3회 이상** 실패 반환하면 (empty / session_gone / timeout — 즉 산출물 문제가 아니라 세션 자체가 결과를 못 낸 경우), 부장님(team-leader)은 아래 조건을 **모두** 확인한 뒤 남은 작업을 직접 완결할 수 있다.

> 근거: 실제로 이 단계가 4회 연속 empty 반환했고, 그 사이 `git push` 는 실제로 수행됐는데 PR 생성과 마커 기록만 미완으로 남았다. 재-dispatch 를 반복해도 같은 지점에서 멈춘다 — 남은 일에 git 명령이 없기 때문이다 (GitHub issue #7).

**진입 조건 (하나라도 false 면 진입 금지 — 사용자에게 보고하고 지시를 기다린다)**

| 항목 | 확인 방법 |
|---|---|
| 1 | `dispatch_stage(3_delivery.pr)` 가 3회 이상 `ok:false` 로 반환됐다 |
| 2 | `origin/<브랜치>` 가 이미 존재한다 (**push 가 끝나 있다**) — `git ls-remote` 는 부장님 권한 밖이므로 직전 publisher 세션 로그 또는 `hang_history` 로 확인 |
| 3 | 남은 작업에 **git 명령이 하나도 없다** — PR 생성(MCP)·마커 기록(`state.sh`)뿐이다 |
| 4 | `escalate: true` 를 받지 않았다 (받았으면 재디스패치·대체 실행 모두 금지, 사용자 에스컬레이션만) |

**허용 범위 (이것만 한다)**

- `bitbucket_createPullRequest` / `bitbucket_getPullRequest` / `bitbucket_updatePullRequest` — MCP 호출이며 git 명령이 아니다.
- `state.sh set` 으로 §완료 기록의 마커 기록.
- `gates/stage7-post-pr-verify.sh` 실행.

**금지 (조건 2 가 거짓이면 그냥 막힌다)**

- `git push` 를 비롯한 모든 git 명령. 부장님은 permission 이 deny 이고, 우회하지 않는다. push 가 남아 있으면 이 대체 경로를 쓸 수 없다 — 사용자에게 보고한다.

**보고**: `[3_delivery.pr PUBLISHER FALLBACK] publisher <N>회 실패 → 남은 작업(PR 생성·마커)에 git 없음을 확인하고 부장님이 직접 완결. push 는 <세션 ID> 에서 이미 완료됨`
